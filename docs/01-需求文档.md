# 需求文档

## 2026-04-21 项目文档初始化与硬件移植需求梳理

### 原始需求

本工程从开源小智工程 fork 而来，已在 `docs` 目录新增当前硬件的原理图。当前目标是先将小智已有功能移植到现有硬件，再在此基础上优化交互功能。希望先按专业开发流程整理相关设计文档和设计架构，作为后续开发依据。

### 背景

- 当前仓库是多板型 ESP-IDF 工程，已具备较成熟的软件主干能力，包括：
  - 音频采集、编码、解码与播放。
  - WebSocket / MQTT+UDP 云端通信。
  - 唤醒词、VAD、状态机、显示、灯效、MCP 工具扩展。
  - 板级抽象和多开发板适配机制。
- 当前新增了目标硬件原理图，但尚未建立面向本项目的定制化需求、架构和实施文档。
- 已从原理图初步确认的信息：
  - 主控为 `ESP32-S3`。
  - 板载 `8MB PSRAM + 16MB Flash`。
  - 存在显示、音频、RGB 灯、IO 扩展等外设资源。

### 目标

- 建立一套可持续维护的项目文档体系，支撑后续“硬件移植 -> 功能验证 -> 交互优化”流程。
- 明确当前硬件移植阶段的业务目标、技术范围、阶段划分和验收标准。
- 明确后续交互优化阶段的设计重点和边界，避免在移植阶段过早引入 UI/交互重构风险。
- 为后续新增目标板目录、引脚映射、驱动适配、配置打包和测试验证提供依据。

### 范围

本阶段纳入范围：

- 项目级需求梳理。
- 系统架构和板级适配架构整理。
- 当前硬件移植阶段的任务分解。
- 后续交互优化阶段的设计入口定义。
- 开发、测试、交付、回滚流程文档化。

本阶段不纳入范围：

- 直接编写目标板驱动代码。
- 对现有音频链路、协议栈或 MCP 能力进行功能重构。
- 在硬件关键器件型号未确认前，固化具体引脚和驱动实现。

### 阶段划分

#### 阶段 A：硬件移植与基础能力打通

目标是让当前硬件稳定运行小智已有核心功能。

关键能力包括：

- 固件可编译、可烧录、可启动。
- 网络可连接。
- 音频输入输出链路可工作。
- 云端协议可建立会话。
- 基础 UI/LED/按键状态反馈可工作。
- 设备激活、对话、升级链路可闭环。

#### 阶段 B：交互体验优化

目标是在阶段 A 稳定后，优化用户可感知体验。

重点方向包括：

- 唤醒到响应的速度与流畅性。
- 说话中、思考中、播报中的状态反馈一致性。
- 屏幕与灯效表现优化。
- 按键、触摸、长按等交互动作统一。
- 错误场景和弱网场景的用户提示优化。

### 约束

- 必须遵循现有上游项目的板级抽象方式，避免直接修改公共逻辑以适配单一硬件。
- 必须为当前硬件创建独立板型标识，避免与已有板型共用 OTA 通道。
- 需要基于 ESP-IDF 5.4+ 和当前项目分区体系进行设计。
- 当前原理图尚未转化为结构化引脚表，文档必须保留待确认项。

### 待确认资料

- 目标板正式命名和 SKU。
- 显示屏分辨率与是否带触摸。
- 音频方案中的最终麦克风通道启用策略。
- 按键、RGB 灯、振动、电池、电源管理、充电管理的引脚与工作电平。
- 是否仅支持 Wi-Fi，或保留 4G / 摄像头 / 其他扩展能力。

### 已补充确认

- 液晶屏驱动芯片为 `ST7789`。
- 摄像头模组型号为 `GC0308`。
- 当前板级引脚可认为与现有 `lichuang-dev` 板型一致或接近。

### 验收标准

- 已形成可直接纳入仓库的项目文档体系，至少包含需求、方案、开发、交付四类文档。
- 方案文档能够指导后续创建新板型目录和实施板级适配。
- 文档中明确区分已确认信息、工程假设、待确认项和风险点。
- 文档中明确阶段目标、模块边界、验证策略和交付方式。
