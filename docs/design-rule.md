# 项目工作流程规则

**重要：当用户提出任何需求时，你必须严格遵守以下五步流程，不得跳过任何步骤，除非确实不需要执行（例如，更新文档），且每一步都必须基于上一步的结果进行，最后的提交代码一定要执行。下面的步骤里要求记录的时间都是实际发生的时间，而不是任务需求描述里的截止时间！**

### 第1步：需求分析
- **目标**：分析当前用户需求，形成简洁清晰的需求文档。
- **输出**：将分析结果写入到 `docs/01-需求文档.md` 文件。该文件必须包含**原始需求**、**目标**、**范围**、**验收标准**这三个核心部分。
- **要求**：内容要简洁、清晰，避免冗余，每次新需求按日期新起一个大段落，标题里记录该次需求的日期！倒序排，新的加在最上面，同一天的需求合并到1个段落里。

### 第2步：方案设计
- **目标**：基于上一步的`docs/01-需求文档.md`，进行详细的技术方案设计。
- **输出**：将设计结果写入到 `docs/02-方案文档.md` 文件。必须包含**架构**、**接口**、**模块/类关系图**、**核心流程时序图**。
- **要求**：使用 Mermaid 或其他文本图表语言描述关系图和时序图。内容要简洁、清晰，每次新需求按日期新起一个大段落，标题里记录该次需求的日期！倒序排，新的加在最上面，同一天的需求合并到1个段落里。

### 第3步：编码实现
- **目标**：根据 `docs/02-方案文档.md` 进行代码编写。
- **要求**：
    - **必要注释**：为复杂逻辑、关键算法和对外接口添加必要注释，解释“为什么这么做”，而不是复述代码本身。
    - **标记 TODO**：对于未完成或需要优化的部分，使用 `// TODO:` 标记。
    - **标记风险点**：对于实现中可能存在的隐患或不确定的地方，使用 `// RISK:` 标记并说明原因。
    - **更新README.md**：更新README.md文件中的与本次开发相关的内容。
    - **记录开发内容**：记录到`docs/03-开发文档.md`，每一次开发按日期新起一个大段落，标题里记录该次需求的日期！倒序排，新的加在最上面，同一天的需求合并到1个段落里。开发内容简明扼要的记录：当前状态、改动记录、未完成项。
    - **记录交付内容**：记录到`docs/04-交付文档.md`，每一次开发按日期新起一个大段落，标题里记录该次需求的日期！倒序排，新的加在最上面，同一天的需求合并到1个段落里。简明扼要的记录：部署、配置、测试、回滚等内容。

### 第4步：补齐测试
- **目标**：为新功能编写完整的测试用例。
- **要求**：
    - **必须包含**：单元测试、边界测试、mock 数据、集成测试建议。
    - **最终标准**：所有编写的测试用例必须能够**全部通过**。

### 第5步：提交 Git Commit
- **目标**：将完成的代码和文档提交到 Git 仓库。
- **要求**：每次提交信息必须严格按照以下格式，包含所有必要字段：

```
<type>(<scope>): <任务ID> - <改动摘要>
```

- 任务ID: <任务ID，如果没有就用提需求里的任务名称>
- 改动摘要: <简要描述本次改动的核心内容>
- 涉及模块: <列出本次改动影响的模块或文件>
- 测试情况: <描述测试结果，如“全部通过”、“单元测试通过”等>
- 风险说明: <指出可能的风险点>
- 回滚方案: <提供明确的回滚指令，如“git revert <commit-hash>”>

`type` 建议使用 `feat`(新功能), `fix`(修复), `docs`(文档), `test`(测试) 等。

- **流程自检**：在开始任何一步骤前，请先确认上一步骤的产物（如`docs/`下的文档）已存在且内容有效。若用户要求中途更改需求，请建议重新从第1步开始。
